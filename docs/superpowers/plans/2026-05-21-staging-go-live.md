# Staging Go-Live Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Stand up a production-like staging environment for Statly, run the go-live smoke and evidence gates against it, and produce a clear go/no-go recommendation.

**Architecture:** Use Vercel as the staging web runtime and a separate Firebase project as the staging data/auth boundary, with production-like auth, cron, ETL, metrics, and admin token policy. Reuse the existing executable contracts in `Scripts/go-live-staging-preflight.ts` and `Scripts/go-live-evidence-check.ts` so staging readiness is machine-checkable rather than prose-only.

**Tech Stack:** Next.js 15, Vercel, Firebase Auth, Firestore, Firebase Admin SDK, Prisma, Redis/Socket.IO where configured, Vitest, ESLint, existing Statly go-live scripts.

---

## Current Findings

- `package.json` already provides the release gates: `typecheck`, `lint`, `guard:routes`, `guard:design`, `test`, `branch:complete`, `build:release`, `go-live:staging-preflight`, and `go-live:evidence-check`.
- `vercel.json` already defines scheduled Vercel cron routes for `/api/cron/daily` and `/api/cron/live-stats`.
- `.firebaserc` currently has one Firebase project alias: `default = statly-4cbed`. Staging should use a separate Firebase project or a clearly isolated staging alias before any shared test traffic.
- `docs/GO_LIVE_TEST_EXECUTION_REPORT.md` says the remaining launch gaps are production-like staging smoke, production-grade Web Vitals/performance evidence, and cross-browser evidence.
- `Scripts/go-live-staging-preflight.ts` already fails closed unless staging has production-like policy: non-local runtime, auth bypass disabled, admin/cron/ETL tokens, Firebase admin credentials, HTTPS base URL, smoke account, fixture league/draft IDs, read-only mutation scope, cleanup policy, monitoring URL, build ID, and full browser matrix.
- `Scripts/go-live-evidence-check.ts` already validates final release evidence for commands, routes, workflows, browser matrix, accessibility, Web Vitals, degraded state, risks, blockers, rollback plan, and post-deploy smoke.

  - If smoke data cannot be created safely without local-only fixture assumptions, stop and write a separate plan for a staging-safe fixture seeder before mutating staging data.

## Operational Risks

- Accidentally pointing staging at production Firebase is a launch-blocking configuration error.
- Running local dev fixture scripts against staging is not approved by this plan.
- Smoke mutations must be fixture-owned and resettable before they are allowed beyond read-only preflight.
- Vercel preview cron behavior may differ from production cron behavior; cron endpoints still need token checks and direct route evidence.
- Cross-browser manual evidence can be inconsistent unless screenshots, console logs, and network failures are captured consistently.
